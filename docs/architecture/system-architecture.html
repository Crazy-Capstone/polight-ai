분석은 비동기

202 → 콜백

증권 1건 분석이 3분 내외다. AI 서버는 접수만 응답하고 백그라운드로 처리한 뒤 Spring 콜백으로 결과를 보낸다. 응답을 기다리는 커넥션이 없다.

약관 연결은 백엔드 책임

이름 → 카테고리

AI는 "어느 약관인가"를 판단하지 않는다. 증권에서 읽은 보험사·상품명을 콜백으로 넘기면 Spring이 policy_terms에서 찾아 담보별 규칙까지 붙인다.

검색은 하이브리드

벡터 + BM25

pgvector 코사인 검색과 한국어 접두 n-gram BM25를 RRF로 융합하고 MMR로 중복 조항을 걷어낸다. 반복되는 표준 조항이 상위를 잠식하는 문제를 막는다.

서버 대 서버 인증

X-Internal-Api-Key

/internal/** 구간은 사용자 토큰이 없다. 양쪽이 같은 시크릿을 쓰고, 키가 없으면 Spring은 내부 경로를 전부 거부하고 AI 서버는 기동 자체를 실패한다.

개인정보는 남기지 않는다

증권 = 휘발성

증권에는 피보험자 이름·생년월일·증권번호가 있다. Upstage 업로드 파일은 분석 직후 삭제하고, 내려받은 PDF도 지운다. 청킹·임베딩도 하지 않는다.

배치 구성

EC2 한 대, 컨테이너 세 개

AI 서버는 Spring과 같은 인스턴스에 올린다. 분석 1건(182초) 동안 CPU 평균 0.1%·메모리 최대 189MB로 실측되어 경합 근거가 없었고, 같은 호스트면 DB 컨테이너에 도커 네트워크로 그대로 붙는다. 다만 compose 프로젝트는 분리한다 — 같은 compose에 넣으면 Spring을 배포할 때마다 3~4분 돌던 분석이 통째로 날아가고 콜백이 오지 않는다.

왜 RDS가 아닌가

운영 DB는 같은 EC2의 pgvector/pgvector:pg16 컨테이너다. VPC·보안그룹·서브넷을 맞추는 작업이 사라지고, AI 서버는 postgres:5432라는 이름만 알면 된다. 대신 인스턴스 사양이 선행 조건이다 — 1GB 인스턴스에서는 AI 컨테이너를 올리는 순간 OOM 킬러가 가장 큰 프로세스인 JVM을 먼저 죽인다.

메모리 한도를 명시한 이유

JVM의 MaxRAMPercentage=75는 cgroup 한도를 읽는다. 한도가 없으면 호스트 전체(4GB)의 75%를 자기 몫으로 계산해 힙을 3GB까지 늘리고, 한 번 늘린 힙은 거의 반납하지 않는다. AI 이미지 빌드 피크와 겹치면 백엔드가 죽는다. 그래서 backend 1280m / postgres 512m로 못 박았다.

플로우 01 · 증권 분석

업로드 한 번에 담보 표가 만들어지기까지

사용자가 증권을 올리는 순간 분석이 시작된다. 업로드와 분석 시작을 두 번 호출할 이유가 없어 CertificateAnalysisStarter가 이어붙인다. 이후는 전부 비동기다 — 응답을 기다리는 쪽은 아무도 없고, 상태는 analysis_results 한 행이 대표한다.

증권과 약관은 같은 입구, 다른 경로

엔드포인트는 POST /internal/analysis 하나다. 8번에서 갈린다. CERTIFICATE는 Studio Agent로 담보를 읽고 끝난다(DB 미사용). TERMS는 조항 단위 청킹 → 임베딩 → policy_chunks 저장까지 간 뒤 같은 형태의 콜백을 보낸다. 요청에 documentType이 없으면 페이지 수(10쪽 이하 = 증권)로 판별하는 안전망이 돈다.

두께로 가르는 판정은 폐기했다. 증권 2장과 약관 153장을 한 파일로 발급하는 보험사가 있어, 오분류는 “에이전트가 증권 고유 항목(증권번호·보험기간·보험사)을 뽑았는지”로 판정한다.

실패는 사용자 문구와 로그를 분리한다

분석 실패 사유는 analysis_results.failure_reason에 영구 저장되고 화면에 뜬다. 그래서 presigned URL이나 PDF 비밀번호 같은 값은 사용자 문구에 넣지 않는다.

  • 비밀번호 있는 파일 — “비밀번호를 입력하거나 해제한 뒤 다시 시도해 주세요”
  • 증권이 아닌 문서 — “보험 증권 파일인지 확인해 주세요”
  • 담보 0건 — “증권 원본 파일인지 확인해 주세요”
  • 설정 누락(에이전트 ID 등) — “관리자에게 문의해 주세요” (재시도 안내를 하지 않는다)
  • 예상 못 한 예외 — 메시지를 노출하지 않고 traceback + analysisResultId로 추적
플로우 02 · 약관 색인

약관은 미리, 배치로 넣는다

약관은 사용자마다 다르지 않다. 같은 상품 가입자 전원이 같은 조항을 적용받으므로, 운영자가 공시자료에서 받은 약관을 미리 한 번 파싱·임베딩해 공용 테이블에 넣는다. 서비스 런타임에는 이 파이프라인이 돌지 않는다 — 챗봇은 이미 색인된 것을 검색만 한다.

공용 약관과 사용자 업로드 약관을 한 테이블에서 가른다

구분값뜻
verification_statusVERIFIED운영자가 확인한 공용 약관. 같은 상품 가입자 전원이 같은 행을 공유한다. (보험사, 상품, 개정판)마다 하나만 존재하도록 부분 유니크 인덱스가 걸려 있다.
verification_statusUNVERIFIED사용자가 올린 약관. 올린 사람에게만 보인다. 확인 전에 공용으로 쓰면 잘못된 파일 하나가 가입자 전원의 답변 근거를 오염시킨다.
sourceOFFICIAL / USER_UPLOAD출처. 확인 상태와 별개로 둔다 — “사용자가 올렸지만 운영자가 확인해 공용이 된 약관”에서 출처를 잃지 않기 위해서다.
revisioneffective_date같은 상품도 약관은 개정된다. 개정판을 다른 행으로 두고, 증권이 적용받았을 시점으로 하나를 고른다.

증권과 약관을 잇는 공통 키 — 표준 보장 카테고리 8종

증권에는 “해외여행중 휴대품손해 특별약관”, 약관에는 “기본형 휴대품 손해”라고 적혀 있다. 글자로는 영영 만나지 못하므로 양쪽을 같은 분류값으로 환산한다. 식별자가 아니라 분류값이라는 점이 중요하다 — 뒤에 나오는 연결에서 후보가 하나로 좁혀질 때만 근거로 쓴다.

플로우 03 · 증권 ↔ 약관 연결

“이 증권은 어느 약관을 적용받는가”

AI는 이 판단을 하지 않는다. 콜백으로 보험사·상품명만 넘기고, 백엔드가 두 번의 단계적 매칭으로 연결한다. 두 단계 모두 위에서 붙으면 아래는 보지 않고, 선언 순서가 곧 신뢰도 순서다. 애매한 후보를 붙이는 것보다 비워 두는 편이 안전하다 — 다른 상품의 약관을 근거로 “보장되지 않습니다”라고 답하면 사용자는 받을 수 있는 보험금을 포기한다.

보장 상세 화면은 두 영역을 합쳐 만든다

가입 사실(coverage_items)은 증권에서 나오고 그 사용자만의 것이다 — 무엇을 얼마에 샀는지. 약관 사실(policy_terms_coverages)은 약관에서 나오고 같은 상품 가입자 모두에게 같다 — 면책·세부한도·청구서류. 한쪽만으로는 화면이 서지 않는다. 증권에는 “해외여행중 상해의료비 3,000만원”이라는 표만 있고, 약관만으로는 그 사람이 그것을 실제로 샀는지 알 수 없다.

뒤늦게 약관을 넣었을 때

약관을 새로 적재하면 이미 끝난 분석들은 여전히 연결이 비어 있다. 그때 POST /internal/terms/backfill을 손으로 한 번 돌린다 (MISSING_TERMS · RELINK_COVERAGES · REMATCH). 스케줄러로 두지 않았다 — 자동으로 돌면 약관을 잘못 적재한 직후에도 그대로 돌아 잘못된 연결이 조용히 퍼진다.

플로우 04 · 챗봇 RAG

질문 하나가 약관 근거를 얻는 경로

AI 서버는 무상태다. 대화 이력을 조회하지 않고 요청에 실린 것만 본다 — chat_messages 조회 권한을 AI 계정에 주지 않기 위한 결정이라, 이력을 자르는 책임은 백엔드에 있다. 트랜잭션도 LLM 호출 밖에 있다. 수 초 걸리는 호출을 트랜잭션 안에서 하면 동시 질문이 커넥션 풀을 말린다.

왜 MMR인가

약관은 같은 표준 조항이 보통약관과 여러 특약에 반복된다. 유사도만으로 top-8을 뽑으면 반복본이 자리를 다 차지한다. 실측에서 “임신·출산 치료비” 질의의 top-8이 사실상 3종류였고 정답 청크는 15위로 밀려 컨텍스트에 들지 못했다 — LLM은 받은 근거만 보고 “언급 없음”이라 답했다. 검색이 원인이었다.

왜 한국어 접두 n-gram인가

“휴대품을 / 휴대품의 / 휴대품이”처럼 조사가 붙어 어절이 매번 달라진다. 글자 bigram은 어절 경계를 넘는 조각을 대량으로 만들어 순위를 무너뜨렸다(Recall@8 83% → 25%). 어간이 앞에 오는 한국어 특성을 이용해 어절 안에서 앞에서부터 자르는 접두 n-gram을 쓴다.

왜 증권 담보를 프롬프트에 넣나

약관에는 그 상품이 팔 수 있는 모든 특약이 실려 있다. 가입하지 않은 담보를 물어도 조항이 검색되어 “보상됩니다”라는 틀린 답이 나간다. 한도 역시 약관에는 “보험가입금액을 한도로”라고만 적혀 있어 자기부담금 같은 값은 증권에서만 얻을 수 있다.

비동기를 견디게 하는 숫자들

비동기 설계의 대가는 “아무 일도 일어나지 않는 실패”다. 콜백이 오지 않으면 에러도 로그도 없이 화면만 멈춘다. 아래 값들은 그 상태가 생기지 않게 하거나, 생겼을 때 빠져나오게 하려고 정한 것이다.

구간값없으면 무슨 일이 생기나
분석 요청 Spring→AIconnect 3s · read 10s · 3회 / 500ms최종 실패하면 그 자리에서 FAILED로 내린다. 요청이 전송되지 않은 분석을 PROCESSING으로 남기지 않는다.
챗봇 질의 Spring→AIread 60s검색 + LLM 생성이 끝날 때까지 기다린다. 분석용 10s를 그대로 쓰면 정상 응답을 타임아웃으로 오인한다.
PDF 다운로드3회 (2s · 4s) · 4xx 즉시 중단이 단계 실패가 곧 분석 전체 실패다. 다만 4xx(만료·권한)는 기다려도 같으므로 재시도하지 않는다.
증권 에이전트 폴링2s 간격 · 최대 180s잡이 끝나지 않는 경우를 잘라낸다. 실측 분석 1건이 182초여서 상한을 그 근처에 뒀다.
콜백 AI→Spring3회 지수 백오프(2s · 4s)Spring 재배포처럼 몇 초 뒤 살아나는 상황이 대부분이다. 400·401은 재시도해도 같아 즉시 포기한다.
콜백 수신멱등 (삭제 후 재삽입)같은 본문이 여러 번 도착해도 결과가 같고, 부분 저장 상태로 남지 않는다.
고착 분석 회수1분 주기 · 10분 초과 시 FAILED콜백이 영영 오지 않으면 프론트 폴링이 끝나지 않는다. 사용자가 상황을 알고 재시도할 수 있게 내려준다.
presigned GET15분URL은 DB에 저장하지 않고 요청 직전에 object key로 서명한다. 유출돼도 수명이 짧다.
업로드 상한파일 30MB · 요청 35MB기본값 1MB로는 실제 약관 PDF를 받을 수 없다. 요청 상한은 여행 정보 파트까지 포함하므로 더 크게 둔다.
대화 이력6개(3턴)프롬프트 길이를 예측 가능하게 유지한다. 양쪽이 합의한 값이라 같이 움직여야 한다.

보안 경계

  • 사용자 구간 — 카카오 OAuth로 로그인하고 서비스 JWT(1시간)로 이후 요청을 인증한다.
  • 서버 대 서버 구간 — /internal/**은 사용자 토큰이 없다. 공유 시크릿 X-Internal-Api-Key 하나로 양방향 인증한다.
  • 타이밍 공격 방어 — 키 비교는 MessageDigest.isEqual. String.equals는 첫 불일치에서 반환해 응답 시간으로 한 글자씩 알아낼 수 있다.
  • fail closed — 키가 없으면 Spring은 내부 경로를 전부 거부하고, AI 서버는 SPRING_BASE_URL이 설정된 환경에서 기동 자체를 실패한다. “설정을 잊었는데 조용히 열려 있는” 상태가 가장 위험하다.
  • 포트 — 외부에 열린 것은 백엔드 80뿐. AI 8000과 DB 5432는 도커 네트워크 안에만 있다.
  • 개인정보 — 증권 원본은 Upstage에서 삭제(DELETE /v2/files)하고 로컬 파일도 지운다. 청킹·임베딩도 하지 않아 공유 인덱스에 섞이지 않는다.
  • 프롬프트 — 피보험자 이름·생년월일·증권번호는 AI 요청 스키마에 아예 없다. 담보명·한도·조건 문구만 넘긴다.
  • 로그 — 요청 진단은 키 존재 여부·개수·길이만 남긴다. PDF 비밀번호와 presigned URL은 사용자 문구·로그에 넣지 않는다.
  • 약관 격리 — UNVERIFIED 약관은 올린 사용자에게만 보이고, 주인 없는 행은 CHECK 제약으로 아예 생기지 않는다.
데이터

한 데이터베이스, 두 소유자

스키마를 바꿀 수 있는 주체는 Flyway 하나다(ddl-auto: validate). 엔티티와 실제 스키마가 다르면 Hibernate가 조용히 컬럼을 만드는 대신 기동을 실패시킨다. AI 서버는 스키마를 만들지 않고, 정해진 테이블에만 쓴다.

테이블쓰는 쪽내용
policy_documentsSpring업로드 원본의 object key · 문서 종류(CERTIFICATE / TERMS) · 파싱 상태
analysis_resultsSpring분석 1건의 상태·요약·보험사·상품명·보험기간 · matched_terms_id · 원본 콜백 JSON
coverage_itemsSpring가입 사실 — 증권에서 읽은 담보·한도·조건, 표시 순서, 연결된 약관 규칙
policy_termsAI 배치약관 1건 = 보험사 + 상품 + 개정판. 확인 상태와 출처로 공개 범위를 가른다
policy_terms_chunksAI 배치공용 약관 본문 청크 + vector(1536) · 조항 경로 · 페이지. 챗봇 검색 대상
policy_terms_coveragesAI 배치약관 사실 — 보장 규칙. 하위로 세부항목 · 세부한도 · 청구서류 · 면책조건 4종을 갖는다
policy_chunksAI 런타임사용자가 올린 문서의 청크(사용자·여행·문서에 귀속). Spring이 상태로 필터해 조회한다
chat_sessions · chat_messagesSpring여행별 챗 세션과 대화. AI 서버에는 조회 권한이 없다

policy_chunks는 user_id · analysis_result_id · document_id가 NOT NULL이라 주인 없는 공용 약관을 넣을 수 없다. 공용 약관을 위해 policy_terms_* 계열을 따로 만든 이유이고, 챗봇 검색이 termsId만으로 범위를 정하는 이유다.

배포

같은 인스턴스, 다른 배포 경로

백엔드는 GitHub Actions가 이미지를 만들어 SSM으로 밀어넣는다. AI 서버는 호스트에서 직접 빌드한다 — 이 서버에 buildx가 없어 compose up --build를 쓸 수 없고, 백엔드는 ECR에서 완성된 이미지를 받아 쓰기 때문에 애초에 설치될 이유가 없었다.

기준 코드 — Crazy-Capstone/polight-ai · Crazy-Capstone/Polight-Server, 브랜치 claude/securities-terms-analysis-architecture-rfcy45. 값과 동작은 두 저장소의 소스·설정·마이그레이션에서 직접 확인한 것만 실었다.
